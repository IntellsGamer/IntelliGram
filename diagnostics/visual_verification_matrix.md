# IntelliGram Visual Verification Matrix

This matrix defines the active visual QA scope for IntelliGram’s **currently implemented** Layer 228 / Web K compatibility surface. A passing encrypted regression only establishes a protocol baseline. A row is visually verified only after the configured Web K runtime shows the expected screen state, gateway behavior is free of protocol failures, storage reflects the outcome, and the relevant reload or reopen behavior holds. Historical entries identify normal SharedWorker evidence where applicable; the currently required local HTTP runtime intentionally uses the in-process compatibility fallback, while HTTPS retains its normal Service Worker path for separate verification.

> **Scope boundary:** this is not a claim of complete Telegram parity. Secret chats, calls, bots, payments, stories, premium features, cloud search, full multi-device synchronization, full permissions, and any server API not represented by IntelliGram’s current handlers remain separately unverified or unimplemented.

## Execution Rules

Each scenario is performed on controlled local data only. The browser test must use the runtime configured for that environment: normal worker behavior is required for HTTPS evidence, while the required local HTTP mode uses IntelliGram’s deterministic in-process compatibility fallback without Service Worker registration. `?noWorker=1` is never used to simulate either path. Each defect record must distinguish the visible symptom, the exact gateway request or error where observable, the durable database state, and reload behavior. Repairs require an encrypted regression where practicable, a complete test run, and a separate browser retest of the affected visual path.
